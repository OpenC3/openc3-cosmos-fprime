# F Prime 4.4.1 CFDP test deployment

This builds NASA F Prime's `Ref` deployment at tag **v4.4.1** with `CfdpManager` wired in, so the plugin's CFDP support can be tested against real flight software.

## What `ref-cfdp.patch` changes in `TestDeploymentsProject/Ref`

- **Subtopology:** the `FileHandling` subtopology (FileUplink/FileDownlink) is replaced by `FileHandlingCfdp` (cfdpManager, fileManager, prmDb).
- **CFDP channel 0:** it takes over ComCcsds's FILE slots:
  - downlink PDUs go to `bufferQueueIn[FILE]`, which is APID 3;
  - uplink comes in from the router's `fileUplinkOut`;
  - buffers come from the comms buffer pool.
- **Timing:** `cfdpManager.run1Hz` runs on the 1 Hz rate group.
- **Comm driver:** `Drv.TcpServer` replaces `Drv.TcpClient`, so the deployment listens and COSMOS connects as a client.
- **Telemetry:** the CfdpManager parameter channels are added to the Ref telemetry packets. `ChannelTelemetry` and `PRM_CHANNEL_CONFIG` are too large for a packet, so they are omitted from the packets, but TlmChan still downlinks them as channels.
- **Subtopology build fix:** `FileHandlingCfdp.fpp` is patched to pass the `fileQueueDepth` argument (10) that `CfdpManager::configure` requires. As shipped, v4.4.1's subtopology does not compile.
- **CfdpManager queue:** the queue depth goes from 30 to 100. Each uplinked PDU is a queued `dataIn` message, and a full queue asserts.
- **TM packet spanning:** `ComCcsdsConfig.Aggregator.enablePacketSpanning` is turned on. CfdpManager's default 992-byte chunks make 1011-byte space packets, which overflow an unspanned 1024-byte TM frame and assert in ComAggregator.
- **Rust:** the image installs Rust because Ref's WasmSequencer needs cargo 1.87 or newer.
- **DpCatalog:** it is **not** connected to CfdpManager. In 4.4.1, `fileDoneOut` returns a constant context, which DpCatalog cannot use. Data products are still generated but not downlinked.

Framing is unchanged from Ref, and it matches the plugin defaults:
- CCSDS space packets in TC (uplink) / TM (downlink) frames;
- SCID 0x44, TC VCID 1;
- 1024-byte TM frames with CRC and no randomization.

CfdpManager keeps its default parameters:
- `LocalEid` = 42, the F Prime entity;
- `FileInDefaultDestEntityId` = 100, the COSMOS entity.

## Build and run

```bash
docker build -t openc3-fprime-cfdp fprime-test/
docker run --rm -p 50000:50000 openc3-fprime-cfdp
```

The first build compiles F Prime and takes a while.

### TlmChan or TlmPacketizer

Ref downlinks telemetry through `TlmChan` by default: one channelized packet per channel on APID 1.
To get `TlmPacketizer` instead, build with `TLM_SEND=packetizer`. It sends the `RefPackets` telemetry
packets on APID 4.

```bash
docker build --build-arg TLM_SEND=packetizer -t openc3-fprime-packetizer fprime-test/
docker run --rm -p 50000:50000 openc3-fprime-packetizer
```

`ref-packetizer.patch`, applied after `ref-cfdp.patch`, makes two changes:

- **Telemetry component:** it switches `CdhCore.tlmSend` to `TlmPacketizer`, using the block F Prime ships
  commented out in `CdhCoreTlmConfig.fpp`.
- **Packet contents:** it puts `CdhCore.tlmSend.GroupConfigs` and `SectionEnabled` into the `CDH` packet.
  Ref has those two lines commented out, and FPP rejects a packet set that leaves a channel out without
  omitting it.

Things that behave differently with TlmPacketizer:

- **Omitted channels:** the channels in the packet set's `omit` list are never downlinked. These are the
  CfdpManager's `ChannelTelemetry` and `PRM_CHANNEL_CONFIG`, plus Ref's own omissions.
- **Packet groups:** packets are sent on change, and only for the enabled groups. Ref starts at level 1.
  `CDHCORE.TLMSEND.SET_LEVEL 3` enables every group, and `SEND_PKT` forces out a single packet.
- **CFDP procedure:** `cfdp_test.py`'s `test_telemetry_still_flows` waits for the channelized
  `REF.SYSTEMRESOURCES.CPU` packet, so run the CFDP procedure against the TlmChan image.

The FPRIME target is generated from the packetizer image's dictionary. The TlmChan build's dictionary is
the same apart from the `CdhCore.tlmSend` component: it lacks the packetizer's commands, channels,
parameters and events, and adds two TlmChan events. So the one target works against both images. The
only difference is that those two TlmChan events show up as unknown event IDs.

`targets/FPRIME/procedures/tlm_test.py` runs against either image. It detects the mode from which
telemetry arrives, then checks command counters, version strings, and TypeDemo's scalar and enum structs.
In packetizer mode it also checks a string inside a struct and the packetizer's group levels.

When COSMOS runs in Docker on the same machine, the plugin's defaults (`host.docker.internal:50000`) connect to it.

## Files in the container

| Path | Purpose |
|------|---------|
| `/files/small.txt`, `/files/medium.bin`, `/files/odd.bin` | Sample files to pull with `SENDFILE`. They are generated by `make_files.py`. |
| `/files/uplink/` | A writable place to push files to |
| `/RefTopologyDictionary.json` | The dictionary the FPRIME target is generated from |

To regenerate the sample files, run `python fprime-test/make_files.py fprime-test/files`.

## Regenerate the FPRIME target

```bash
docker run --rm --entrypoint cat openc3-fprime-packetizer /RefTopologyDictionary.json > fprime-test/RefTopologyDictionary.json
python lib/fprime_parser.py FPRIME fprime-test/RefTopologyDictionary.json
```

See the main README's "CFDP with CfdpManager" section for configuring the OpenC3 CFDP plugin against this deployment. The end-to-end procedure is `targets/FPRIME/procedures/cfdp_test.py`.
